Blindspot

git blame tells you who wrote it.
Blindspot tells you who read it.

코드가 사람이 읽는 속도보다 빨리 만들어지는 시대에, 아무도 측정하지 않는 지표가 하나 있다. 테스트가 얼마나 코드를 지나갔는지는 재면서, 사람의 눈이 얼마나 지나갔는지는 아무도 안 잰다. Blindspot은 커밋 직전에 그 숫자를 보여준다.

이 카드의 숫자는 하나의 정의에서 나온다

여기 보이는 모든 값은 실제 스코어링 모델이 실제 세션 데이터(182줄, 5개 파일)를 계산한 결과다. 하드코딩된 숫자는 하나도 없다. 아래 슬라이더로 "읽었다"의 기준을 바꾸면 카드 전체가 다시 계산된다.

the research question

"읽었다"를 어떻게 정의할 것인가

이게 이 프로젝트의 전부다. 나머지(패널, 위험도, git 훅)는 답을 눈에 보이게 만드는 장치일 뿐이고, 답이 틀리면 진행바 달린 거짓말이 된다. 모델은 논쟁할 수 있을 만큼 작게 유지했다 — 관측 가능한 신호 다섯 개, 가중치, 임계값 하나.

signalobservedpts
visible화면에 300ms 이상 떠 있었다+1
focused활성 에디터에서, 창이 포커스된 채로 800ms 이상+1
dwell뷰포트가 1초 이상 멈춰 있었다+1
caret커서를 올렸거나 선택했다+1
edited사람이 직접 타이핑했다+2

기본 임계값 3점은 임의로 고른 값이 아니다. 아래 세 명제가 동시에 참이 되는 가장 작은 값이고, 이 셋은 테스트로 박아뒀다 — 나중에 모델을 바꿔서 하나라도 깨지면 그건 튜닝이 아니라 다른 제품이다.

가중치보다 중요한 건 세지 않는 것들이다. 창이 포커스를 잃으면 아무것도 쌓이지 않고(배경 탭에 하루 띄워놔도 1점), 사람이 읽을 수 없는 속도(45줄/초)로 스크롤하면 가시성 점수가 0이며, 2초보다 긴 틱은 통째로 버린다 — 노트북을 덮어놓고 몇 시간을 "정독"으로 기록하는 걸 막는 유일한 방법이다.

why a percentage alone is useless

36%가 어디의 36%인가

README 40줄을 안 읽은 것과 auth/session.ts 3줄을 안 읽은 것은 같은 사건이 아니다. 그래서 모든 줄은 경로(auth/, billing/, migrations/)와 내용(eval(, process.env, 문자열로 조립한 SQL)으로 위험도가 매겨지고, 리포트는 양이 아니라 위험도 순으로 정렬된다.

커버리지는 무엇에 대한 커버리지였는지에 따라 가중된다. 위 시나리오에서 전체 커버리지는 64%지만 critical 코드 커버리지는 24%다 — 점수가 64가 아니라 49인 이유가 그것이다.

측정할 대상이 없는 항목은 0점 처리하지 않고 빼버린 뒤 가중치를 나머지에 재분배한다. critical 코드를 건드리지 않은 diff가 "critical 0%"로 벌점을 받는 건 말이 안 되니까.

이 시나리오는 전부 새로 추가된 줄이라 New code가 Coverage와 같은 값이 된다. 기존 줄을 수정한 diff에서는 갈린다.

open questions

결정이 필요한 것들

되돌리기 비싼 것 위주로. 각 항목의 기본값은 이미 코드에 들어가 있으니, 그냥 두면 그 선택으로 굴러간다. 전체는 저장소의 docs/QUESTIONS.md에 있다.

Q1 · 액션 필요

레포를 독립시킬 것인가

새 저장소를 만들려 했지만 이 세션의 GitHub 앱 권한으로 레포 생성이 막혀 있었다 (403). 그래서 지금은 프로필 저장소의 브랜치 안에 blindspot/ 디렉터리로 들어가 있다.

GitHub에서 빈 레포 하나 만들고 → scripts/extract-repo.sh 실행 (히스토리 유지, 30초)

Q2 · 캘리브레이션

임계값 3점이 맞나

visible + focused만으로 2점이라, dwell 1초만 붙으면 커서를 옮기지 않아도 3점이 된다. 화면에 띄워놓고 1초 멈춘 것을 "읽었다"로 볼 것인가. 위 슬라이더를 4로 올려보면 얼마나 빡빡해지는지 보인다.

기본값 3 · 하루 써보고 "안 읽었는데 읽었다고 나온" 케이스가 있는지가 유일한 판단 기준

Q3 · 범위

삭제된 줄도 리뷰 대상인가

지금은 아니다 — 없는 줄을 못 읽을 수는 없으니까. 하지만 에이전트가 조용히 지운 null 체크야말로 버그가 숨는 곳이다. 제대로 하려면 diff 뷰 안에서의 어텐션 추적이 필요하다.

추천: 리포트에는 노출하되 점수에는 미반영

Q4 · 제품 방향

커밋을 막을 것인가

기본값은 경고만 하고 통과(exit 0)다. 커밋을 막는 리뷰 도구는 일주일 안에 --no-verify로 우회되거나 삭제된다. 하지만 팀 도구로 갈 거면 CI에서 강제하는 게 자연스럽고, 그러면 "개인 학습 도구"가 아니라 "규정 준수 도구"가 된다.

기본은 경고 · 강제는 --min-coverage로 옵트인

Q5 · 정직성

무엇을 "AI가 쓴 코드"라 부를 것인가

정직하게 말하면 LLM이 썼는지 우리는 알 수 없다. 관측 가능한 건 typed (한 글자씩), bulk(한 번에 8줄/280자 이상 — 에이전트든 붙여넣기든 구분 불가), declared-ai(도구가 명시적으로 선언)뿐이다. 그래서 코드 안에서는 machine-written이라 부른다.

UI에는 "AI-generated"로 표기 중 · 과장이라고 보면 bulk를 버킷에서 빼면 됨 (한 줄)

Q6 · 확장 범위

저자인가 리뷰어인가

지금은 저자의 blindspot을 잰다. 하지만 "LGTM을 3초 만에 누른 리뷰어가 실제로 본 줄은 12%"가 훨씬 강한 메시지다. 문제는 그게 GitHub 웹에서 일어난다는 것 — 브라우저 확장이 필요하고, 그건 다른 프로젝트다.

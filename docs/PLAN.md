## v0.2 — 실제로 써보고 고치기

가장 먼저 할 일. 새 기능보다 이게 먼저다.

1. **F5로 띄워서 하루 써보기.** 확인할 것:
   - dwell 1초가 실제로 "멈췄다"로 느껴지는지 (너무 예민하면 3점이 너무 쉽게 나옴)
   - 45 lines/sec 스크롤 가드가 정상 스크롤을 죽이지 않는지
   - 4초 리프레시 주기에서 `git diff`가 큰 저장소에서 얼마나 걸리는지
2. **큰 저장소 성능.** 파일 500개짜리 diff에서 `collectDiff` + `buildReport`가
   4초마다 도는 게 감당되는지. 안 되면 diff 캐시 + 변경 파일만 재계산.
3. **Undo/redo 처리 재검토.** 지금은 provenance를 `unknown`으로 떨어뜨리는데,
   되돌린 줄의 증거를 어떻게 다룰지 정한 적 없음.
4. **멀티 워크스페이스 / 서브모듈.** 지금은 첫 번째 워크스페이스 폴더만 본다.

## v0.4 — 팀으로 확장

여기서부터는 프라이버시 설계가 먼저다. 개인 어텐션 데이터를 팀에 올리는 순간
"감시 도구"가 되고, 그러면 아무도 안 쓴다.

1. **집계만 올리기.** 개인별 줄 단위 데이터는 절대 저장소를 떠나지 않는다.
   PR 단위 집계(coverage %, critical blindspot 줄 수)만 공유.
2. **PR 코멘트 봇.** "이 PR의 변경 중 31줄이 저자에 의해 검토되지 않았습니다."
3. **리뷰어 커버리지.** 저자가 아니라 *리뷰어*가 뭘 읽었는지가 사실 더 중요하다.
   GitHub 리뷰 UI에서의 어텐션은 브라우저 확장 없이는 못 잡음 — 큰 결정.
   → `docs/QUESTIONS.md` Q6

## v1.0 — 검증

기능이 아니라 증거가 필요한 단계. `docs/RESEARCH.md`의 4단계 실험:

1. 세션 기록 → 리플레이 (하네스는 `demo/simulate.ts`에 이미 있음)
2. 사람이 라벨링한 ground truth ("이 hunk 진짜 읽었어?")
3. 라벨 기준으로 threshold 튜닝 (recall 우선, false "reviewed"가 훨씬 비쌈)
4. **결정적 실험:** 버그가 blindspot에 몰려 있는가?
   버그 수정 커밋 → 원인 커밋 역추적 → 그 줄이 당시 미검토였는지 확인.
   여기서 상관관계가 안 나오면 이 지표는 장식이고, 그러면 접어야 한다.

이 실험은 늦출수록 손해다. v0.3의 커밋 trailer가 데이터 수집의 시작점.

## 안 할 것 (의도적으로)

- **AI 코드만 추적하기.** 문제는 "안 읽은 코드"지 "AI가 쓴 코드"가 아니다.
  AI 종속 확장이 되는 순간 수명이 모델 유행과 묶인다. AI는 서브메트릭 하나로만.
- **커밋 차단을 기본값으로.** 기본은 경고 + exit 0. 커밋을 막는 리뷰 도구는
  일주일 안에 삭제된다. 강제는 `--min-coverage`로 옵트인.
- **게임화 (배지, 연속 기록, 리더보드).** 측정하는 순간 최적화 대상이 된다.
  "커버리지 100%"를 위해 스크롤을 천천히 하게 만들면 이 도구는 실패한 것이다.
- **원격 전송.** 어텐션 데이터는 개인 데이터다. `.git/blindspot/`에서 나가지
  않는다.

# Blindspot

**`git blame`은 누가 한 줄을 작성했는지 알려준다. Blindspot은 누가 그 줄을 읽었는지 알려준다.**

Blindspot은 **변경된 코드(diff) 중 실제로 눈이 머문 줄을 추적**하고, 커밋 직전에 **아직 읽지 않은 코드가 얼마나 되는지** 알려주는 VS Code 확장입니다.

```text
┌─────────────────────────────────┐
│     BLINDSPOT                   │
│                                 │
│ 리뷰 커버리지       64%         │
│ Blindspot           36% ⚠       │
│                                 │
│ 변경된 줄           182         │
│ 검토한 줄           116         │
│ 읽지 않은 줄         66         │
│                                 │
│ ⚠ CRITICAL                      │
│ src/auth/session.ts             │
│ 9-34번 줄 읽지 않음              │
│                                 │
│ [ Blindspot 검토하기 ]           │
└─────────────────────────────────┘
```

이 카드는 단순한 목업이 아닙니다.

```bash
npm run demo
```

를 실행하면 **실제 점수 계산 모델이 스크립트로 재생한 편집 세션을 기반으로** 위 숫자를 계산합니다.

---

## 왜 만들었나

우리는 코드의 어느 부분이 **테스트에서 실행됐는지**를 측정할 수 있습니다.

하지만 그 코드의 어느 부분을 **사람이 실제로 읽었는지**를 측정하는 지표는 거의 없습니다.

코드를 작성하는 데 걸리는 시간이 가장 길었던 시대에는 큰 문제가 아닐 수도 있었습니다.

하지만 지금은 다릅니다.

**AI는 사람이 읽는 것보다 훨씬 빠르게 코드를 만들어낼 수 있습니다.**

그 결과 AI 코딩 환경의 자연스러운 실패 모드는 다음과 같아집니다.

> 크고, 그럴듯하고, CI를 통과하지만
> 아무도 제대로 읽지 않은 변경 사항.

Blindspot은 바로 이 문제를 측정합니다.

**아무도 제대로 측정하지 않는 것 — 개발자의 코드에 대한 실제 주의(attention) — 를.**

---

## 무엇을 "읽었다"고 판단하는가

이 프로젝트에서 가장 중요한 연구 질문입니다.

전체 판단 모델은 [`src/core/evidence.ts`](src/core/evidence.ts)에 약 30줄 정도로 구현되어 있습니다.

다섯 가지 신호에 점수를 부여하고, 특정 임계값을 넘으면 해당 줄을 **검토된 줄(reviewed)** 로 판단합니다.

| 신호      | 의미                                              | 점수 |
| ------- | ----------------------------------------------- | -: |
| visible | 화면에 300ms 이상 표시됨                                |  1 |
| focused | 활성 에디터에 표시되고, VS Code 창이 포커스된 상태에서 800ms 이상 표시됨 |  1 |
| dwell   | 해당 줄이 화면에 있는 상태에서 뷰포트가 1초 이상 멈춰 있음              |  1 |
| caret   | 커서를 해당 줄에 놓거나 선택함                               |  1 |
| edited  | 해당 줄에 직접 입력함                                    |  2 |

**3점 이상이면 해당 줄을 검토된 것으로 판단합니다.**

이 임계값은 프로젝트가 처음부터 검증하려고 했던 세 가지 가정을 그대로 만족하도록 설정되어 있습니다.

이 내용은 [`test/evidence.test.ts`](test/evidence.test.ts)에 실제 테스트로 작성되어 있습니다.

```text
스크롤하면서 지나감       → 1점   ≠ 검토됨
0.2초 동안 화면에 표시됨  → 0점   ≠ 검토됨
표시 + 멈춤 + 커서       → 3점   ≈ 검토됨
```

또한 다음 상황에서는 어떠한 검토 점수도 부여되지 않습니다.

* VS Code 창이 포커스를 잃은 상태
* 사람이 읽기 어려울 정도로 빠르게 스크롤하는 상태

  * 기본값: 초당 45줄
* 2초가 넘는 단일 측정 구간

그렇지 않으면 노트북을 닫아놓고 한 시간을 기다린 것만으로도 "열심히 코드를 읽었다"는 결과가 나올 수 있기 때문입니다.

이 정의가 무엇을 놓치고 있는지는 [`docs/RESEARCH.md`](docs/RESEARCH.md)에 정리되어 있으며, 이후 실제 사용자 연구를 통해 검증할 계획입니다.

## 단순한 퍼센트만으로는 충분하지 않다

읽지 않은 코드가 36%라고 해서 그것만으로는 아무것도 알 수 없습니다.

README의 중요하지 않은 40줄일 수도 있고, `auth/session.ts`의 위험한 3줄일 수도 있습니다.

그래서 Blindspot은 모든 변경된 줄을 **위험도(risk)** 기준으로 분류합니다.

위험도는 다음을 함께 고려합니다.

**파일 경로**

```text
auth/
billing/
migrations/
.github/workflows/
```

**코드 내용**

```text
eval(...)
process.env
문자열로 조합한 SQL
innerHTML
```

그리고 보고서는

> **위험도 → 변경량**

순서로 우선순위를 정합니다.

예를 들어 중요 파일 내부의 주석은 한 단계 낮은 순위로 처리됩니다.

> 중요한 인증 버그가 주석 안에 있는 것은 아니니까요.

## Review Score

단순히 "64% 읽었다"라고 말하는 대신, **무엇을 읽었는가**까지 반영한 종합 점수를 제공합니다.

```text
Review Score

█████░░░░░ 49

Coverage       64%
Critical       24%     ← 그래서 점수가 64가 아니라 49
New code       64%
AI-generated   48%
```

Review Score는 **코드 커버리지에 위험도를 반영한 가중치**를 적용해 계산합니다.

측정할 대상이 없는 항목은 평가에서 제외하고, 해당 항목의 가중치를 다른 항목으로 재분배합니다.

예를 들어 변경 사항에 critical 코드가 하나도 없다면,

> "critical 코드를 안 읽었기 때문에 감점"

같은 이상한 결과는 나오지 않습니다.

## AI 코드는 하나의 분류일 뿐이다

Blindspot을 AI 코드만 추적하는 도구로 만들지는 않았습니다.

그렇게 하면 오히려 핵심 문제에서 멀어집니다.

중요한 것은 **누가 작성했는가가 아니라, 변경된 코드가 검토되었는가**이기 때문입니다.

따라서 Blindspot은 모든 변경된 줄을 동일한 방식으로 측정하고,

**AI 작성 여부는 리뷰 커버리지와 나란히 제공되는 정보**로 취급합니다.

프로비넌스(provenance)는 추측하지 않고 실제 관찰된 정보만 기록합니다.

| 유형            | 의미                                                       |
| ------------- | -------------------------------------------------------- |
| `typed`       | 사람이 키 입력으로 작성                                            |
| `bulk`        | 에이전트, 붙여넣기, codemod 등으로 한 번에 삽입됨                         |
| `declared-ai` | 도구가 `.blindspot/ai-regions.json`을 통해 AI 생성 영역임을 명시적으로 선언 |
| `unknown`     | Blindspot 추적 시작 이전에 존재했던 코드                              |

## CLI

```bash
blindspot check --staged            # 커밋 예정 변경 사항의 리뷰 카드 출력
blindspot report                    # 파일별 리뷰 현황 출력
blindspot check --min-coverage 70   # 커버리지 70% 미만이면 종료 코드 1
blindspot check --json              # 기계가 읽을 수 있는 JSON 출력
```

기본으로 설치되는 pre-commit hook은 **경고만 출력하고 종료 코드 0을 반환**합니다.

리뷰 도구가 커밋 자체를 막아버리면 아마 일주일 안에 제거될 것입니다.

Blindspot의 철학은:

> **커밋을 막는 도구보다, 사실을 알려주는 도구가 오래 살아남는다.**

강제 정책이 필요한 경우 다음 옵션을 사용할 수 있습니다.

```bash
--min-coverage
--max-critical
```

## 설정

에디터 설정은 `blindspot.*` 아래에서 관리합니다.

프로젝트 전체에서 사용하는 위험도 규칙은 커밋 가능한:

```text
.blindspot/config.json
```

에 정의할 수 있습니다.

예:

```json
{
  "reviewThresholdPoints": 3,
  "minCoverage": 70,
  "maxCriticalBlindspotLines": 0,
  "pathRules": [
    {
      "pattern": "(^|/)payments/",
      "level": "critical",
      "reason": "money movement"
    }
  ]
}
```

이렇게 하면 팀 전체가 **무엇을 위험한 코드로 판단할지**에 대해 동일한 규칙을 사용할 수 있습니다.

## 데이터는 어디에 저장되는가

리뷰 상태는 다음 위치에 저장됩니다.

```text
.git/blindspot/state.json
```

Git 저장소 내부에 있기 때문에:

* 저장소별로 독립적이고
* 실수로 커밋될 일이 없으며
* 저장소를 삭제하면 함께 사라집니다.

중요한 원칙도 있습니다.

> **리뷰 데이터는 개인 텔레메트리이며 절대로 공유 브랜치에 올라가서는 안 됩니다.**

Blindspot의 데이터는 외부로 전송되지 않습니다.

**모든 데이터는 로컬 컴퓨터에만 존재합니다.**

## 줄의 정체성

Blindspot은 줄 번호 자체에 리뷰 증거를 저장하지 않습니다.

대신 **각 줄의 내용 해시(content hash)** 를 기준으로 증거를 연결합니다.

따라서:

```text
import foo

const a = 1
```

에서 `import bar`를 위에 추가하더라도,

이미 읽었던:

```text
const a = 1
```

의 리뷰 증거가 다른 줄에 잘못 전달되지 않습니다.

마찬가지로:

* 들여쓰기 변경 → 기존 증거 유지
* 토큰이 실제로 변경됨 → 새로운 줄로 취급

합니다.

## 아키텍처

```text
src/core/        모델 계층 — vscode import 없음, 완전한 단위 테스트 가능
  evidence.ts      다섯 가지 신호 → 점수 → reviewed 판정
  risk.ts          경로 + 코드 내용 → 위험도 계산
  ledger.ts        수정 및 reload 이후 줄의 정체성 추적
  coverage.ts      diff × evidence → 리뷰 리포트
  score.ts         종합 Review Score 계산

src/extension/   VS Code 연동 계층
  tracker          화면 체류 및 편집 이벤트 추적
  panel             리뷰 리포트 UI
  decorations      미검토 코드 표시
  git               Git diff 연동

src/cli/         `blindspot` CLI
  hook              pre-commit hook
  CI                자동화된 리뷰 기준 검사

demo/            스크립트 세션을 실제 모델로 재생
```

`core` 경계를 별도로 둔 이유는 명확합니다.

> **"읽었다"의 정의는 계속 조정될 수 있어야 하고,
> VS Code를 실행하지 않고도 재현하고 검증할 수 있어야 합니다.**

그래야 이 도구가 단순한 IDE 기능이 아니라 실제로 검증 가능한 측정 모델이 될 수 있습니다.

## 연구 질문

Blindspot은 완성된 "정답"을 제시하는 프로젝트가 아닙니다.

오히려 다음 질문을 실험하기 위한 도구입니다.

* 화면에 보였다는 사실이 실제로 읽었다는 증거인가?
* 300ms, 800ms, 1초라는 임계값이 적절한가?
* 커서를 올리는 행동은 정말 리뷰의 증거인가?
* AI가 만든 코드일수록 사람의 리뷰 방식은 달라지는가?
* Review Score가 실제 결함 발견률과 관계가 있는가?
* 개발자가 Blindspot을 의식하게 되면 실제 리뷰 행동이 달라지는가?

즉 Blindspot의 핵심은 확장 프로그램 그 자체보다,

**"코드 리뷰에서 사람의 주의(attention)를 어떻게 측정할 수 있는가?"**

라는 질문에 있습니다.

자세한 내용은 [`docs/RESEARCH.md`](docs/RESEARCH.md)를 참고하세요.

아직 결정되지 않은 문제는 [`docs/QUESTIONS.md`](docs/QUESTIONS.md)에 기록되어 있고, 다음 개발 단계는 [`docs/PLAN.md`](docs/PLAN.md)에 정리되어 있습니다.

## 핵심 아이디어

AI가 코드를 작성하는 시대에는

```text
"누가 코드를 썼는가?"
```

만큼이나

```text
"누가 그 코드를 읽었는가?"
```

가 중요합니다.

**Blindspot은 그 두 번째 질문을 측정하려고 합니다.**

> 코드가 빨라질수록,
> 읽는 사람의 속도는 더 중요해집니다.
>
> 그리고 우리가 아직 측정하지 않았던 것은
> 어쩌면 코드가 아니라 **주의**였을지도 모릅니다.

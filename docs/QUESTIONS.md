## Q2. 리뷰 임계값 3점이 맞나 — 실제로 써보고 판단해야 함

지금 모델:

```
visible(1) + focused(1) + dwell(1) + caret(1) + edited(2) + revisit(1)
reviewed = 3점 이상
```

브리프에 있던 세 부등식이 **정확히** 성립하도록 3으로 잡았다:

```
스크롤만 = 1점 → 미검토 ✓
0.2초 노출 = 0점 → 미검토 ✓
보임 + 멈춤 + 이동 = 3점 → 검토됨 ✓
```

**걱정되는 케이스:** `visible + focused` 만으로 2점이라, 여기에 dwell 1초만
붙으면 커서 안 옮겨도 3점이 된다. 화면에 띄워놓고 1초 멈춘 것만으로 "읽었다"가
되는 건데 — 너무 후한 것 같기도 하다.

focal weighting이 이 걱정을 일부 덜어준다: visible/focused 시간이 이제 커서
거리에 따라 감쇠하므로, 뷰포트 가장자리 줄은 같은 1초로 2점을 못 받는다.
dwell도 초점 근방에만 적립된다. 그래도 커서 바로 옆 줄에 대해서는 걱정이
그대로 남아 있고, 이건 여전히 실사용으로 판단할 문제다.

revisit(1)이 추가되면서 focused 시간이 있는 줄을 두 번에 걸쳐 본 경우에도
3점에 도달한다. 이게 후한지 정당한지도 같은 방법으로 판단해야 한다.

- **후하다고 생각되면:** `blindspot.reviewThresholdPoints`를 4로. 그러면 커서를
  옮기거나 직접 편집해야 검토로 인정됨.
- **판단 방법:** 하루 써보고 "안 읽었는데 읽었다고 나온" 케이스가 있는지 보기.
  그게 이 도구의 유일한 치명적 실패 모드다.

## Q3. 삭제된 줄도 리뷰 대상인가

지금은 **아니다** (세기만 하고 점수엔 안 들어감). 논리는 "없는 줄을 못 읽을 수는
없다".

근데 삭제야말로 버그가 숨는 곳이다. 에이전트가 조용히 지운 null 체크 같은 거.

제대로 하려면 diff 뷰 안에서의 어텐션 추적이 필요하다 (v0.3). 그 전엔:
- (a) 지금처럼 무시 — 지표가 정직하지만 구멍이 있음
- (b) 삭제 hunk를 "미검토"로 리포트에만 노출, 점수엔 미반영
- (c) 점수에도 반영

**내 추천: (b).** 보이긴 하되 점수를 흔들진 않게. 근데 결정은 필요.

→ **(b)로 구현됨.** 파일마다 `−N deleted` 태그, 리포트에 `deletedLines` 합계,
CLI의 Reading 블록에 "N lines removed, not measured". 점수는 그대로.

## Q4. 커밋 차단, 기본값으로 켤까

지금 기본값은 **경고만 하고 통과** (exit 0). 강제하려면 명시적으로
`blindspot check --min-coverage 70`.

이유: 커밋을 막는 리뷰 도구는 일주일 안에 `--no-verify`로 우회되거나 삭제된다.

근데 팀 도구로 쓸 거면 얘기가 다르다 — CI에서 강제하는 게 자연스럽다. 그러면
"개인 학습 도구"가 아니라 "규정 준수 도구"가 되는데, 그건 완전히 다른 제품이다.
**어느 쪽으로 갈지가 사실상 제품 방향 결정이다.**

## Q5. "AI가 생성한 코드"를 어떻게 정의할 것인가

정직하게 말하면 **우리는 LLM이 썼는지 알 수 없다.** 관측 가능한 건 이것뿐:

- `typed` — 사람이 한 글자씩 친 것
- `bulk` — 한 번의 이벤트로 8줄/280자 이상 들어온 것 (에이전트, 붙여넣기, codemod 구분 불가)
- `declared-ai` — 도구가 `.blindspot/ai-regions.json`에 명시적으로 선언한 것
- `unknown`

그래서 코드 안에서는 "AI"라고 단정하지 않고 `machine-written`으로 부른다. UI에는
"AI-generated"로 나가고 있었는데 — **이 두 단어가 다른 게 신경 쓰이면 말해줘.**
붙여넣기까지 AI로 세는 게 과장이라고 보면 `bulk`를 AI 버킷에서 빼고
`declared-ai`만 세도 된다 (한 줄 수정).

→ **표기는 통일됨.** Review Score의 행 이름이 CLI·패널·데모 모두 `Machine-written`
이다 (`CONTEXT.md`의 용어). 사이드바와 호버는 원래부터 그렇게 말하고 있었다.
버킷의 정의(bulk + declared-ai)는 그대로이고, bulk를 빼는 건 여전히 별개의
결정이다.

## Q6. 저자 vs 리뷰어 — 누구의 blindspot을 재는 건가

지금은 **저자**다. 자기가 쓴(혹은 에이전트가 쓴) diff 중 자기가 안 읽은 부분.

근데 진짜 가치는 **리뷰어** 쪽에 있을 수도 있다. "LGTM 3초 만에 누른 리뷰어가
실제로 본 줄은 12%" 같은 거. 이건 훨씬 강한 메시지고 훨씬 정치적으로 위험하다.

문제는 리뷰가 GitHub 웹 UI에서 일어난다는 것 → 브라우저 확장이 필요하고,
그건 완전히 다른 프로젝트다. **VS Code 안에 머무를지, 브라우저까지 갈지**가
v0.4의 갈림길.

## Q8. 마우스 hover를 신호로 쓰는 게 정직한가

hover provider 호출은 "마우스가 그 토큰 위에 멈췄다"는 관측이지 "읽었다"가
아니다. 지금은 두 가지로 쓴다 — attention budget의 초점(커서보다 최근이면), 그리고
`caret`과 같은 *navigated* 1점. 후자가 후하다고 보면 `evaluate()`에서
`pointerHits`를 빼고 초점 선택에만 쓰면 된다 (한 줄). 반대로 마우스가 시선을
더 잘 따라간다고 보면 가중치를 따로 둘 수도 있다. 판단 기준은 Q2와 같다: 하루 써
보고 "마우스만 스쳤는데 읽었다고 나온" 줄이 있는가.

## Q7. 이름

`Blindspot`은 좋은데 VS Code 마켓플레이스에 비슷한 게 있는지 확인 안 했다
(이 컨테이너에서 마켓플레이스 검색이 막혀 있음). 퍼블리시 전에 확인 필요.

대안으로 생각해둔 것: `Unread`, `Seen`, `git seen`, `Attention`.
개인적으로는 `Blindspot`이 제일 낫다고 본다 — "안 본 것"이 제품의 전부니까.
